# 運用ランブック（ローカル研究用）

## 起動とヘルス確認

```bash
python -m app
curl -s http://127.0.0.1:8000/health
curl -s http://127.0.0.1:8000/api/events
```

`/health`はプロセスがHTTP応答できることを示すだけで、DBのバックアップ正常性やOpenAI API稼働は保証しません。

## 画像生成の障害

- `503 not configured`: OPENAI_API_KEYがサーバーに設定されていない。画像生成チェックOFFでもデモは動く。
- `429`: 回数制限。サーバープロセスの再起動でカウンターが消える暫定実装。公開前に永続quotaが必要。
- `502`: OpenAI HTTPエラー、権限/請求上限またはネットワークの問題。キーやAPI応答本文はログに出さない。
- 生成途中にサーバー停止: `image_jobs`が`running`のまま残る可能性。研究環境では該当作品を調べ、データ保全を確認して手作業で修正する。本番はジョブleaseとリカバリータスク実装。

## データ・バックアップ

**テストDB以外の削除に注意。** データディレクトリにはSQLiteと生成画像を保存する。SQLite接続を通じてバックアップを取得し、メディアファイルと同時点の整合性を別途確認する。WALモードのSQLiteでは`.sqlite`だけを不用意にコピーしない。

```python
import sqlite3
src=sqlite3.connect('data/zokuzoku.sqlite')
dst=sqlite3.connect('backup.sqlite')
with dst:src.backup(dst)
dst.close();src.close()
```

個人のプロンプト等を取得し得るため、実ユーザーを扱う前に保存期間、利用目的、ユーザーによる削除要求、バックアップからの消去範囲を定める。

## 監視項目（本番移行時）

APIのp50/p95/エラー率、画像生成回数/課金/失敗率、未処理ジョブ、DBサイズとロック待ち、ポーリング負荷、権利申告審査待ち、通報数、ユーザーと作者の再訪、ユーザーによる画像生成コスト、インサイト判定と実購入誤差。

## 復旧優先順位

1. キー漏洩：キー即時失効 → 新規鍵 → 請求/監査ログ点検。
2. 不適切画像：公開を停止 → 証跡保全 → 権利者/本人/法務対応。
3. DB障害：書き込み停止 → 最新の整合バックアップ確認 → 復元 → イベント整合性確認。
4. 画像生成費の急増：画像API機能停止 → 利用上限/利用者/ジョブ履歴確認。
5. 数理評価の異常：PICSY表示を停止して研究入力を保存。現金移動は実装しない。
